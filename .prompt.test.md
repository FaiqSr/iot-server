# Prompt: Generate Jest unit tests for server (argument: `test`)

Purpose

- Auto-generate Jest + TypeScript unit tests for the Express server code in this repo.
- Focus areas: notification service/controller, sensor-setting service, and related API flows.

Context (what Copilot will have in the workspace)

- The server is an Express + TypeScript project using Prisma, Zod, and firebase-admin.
- Key files to test: `src/service/NotificationService.ts`, `src/controller/NotificationController.ts`, `src/service/SensorSettingService.ts`, `src/__tests__/`.
- Tests must mock external dependencies (`firebase-admin`, `../utils/prisma`) so they run without a real DB or Firebase credentials.

Goal (deliverables)

- Create Jest test files under `src/__tests__/` with TypeScript: e.g. `NotificationService.test.ts`, `NotificationController.test.ts`, `SensorSettingService.test.ts`.
- Tests should use `jest.mock(...)` to stub:
  - `firebase-admin` (provide `messaging().send` mocked)
  - `../utils/prisma` (mock `sensorSetting`, `alat` and other used methods)
  - any other network/DB interactions
- Provide tests for success and error paths, including:
  - NotificationService: success send, invalid token error handling
  - NotificationController.processReading: 404 when no setting, no-notify when within range, send+update when breached and throttling allows, no-send when throttled
  - SensorSettingService.updateSetting: returns updated setting and throws 404 when setting not found
- Use `jest.resetModules()` or fresh requires inside tests where needed so mocks are applied cleanly.

Constraints & Style

- Use TypeScript syntax compatible with the repo `tsconfig.json` (ESNext, commonjs output).
- Place tests under `src/__tests__/` with filenames matching the module under test.
- Keep tests deterministic and not flaky: use fixed dates (`new Date(<ms>)`) when testing throttling.
- Do not modify source code; tests should adapt to existing function signatures.

Example test scaffolding (explain to Copilot what to produce)

- For `NotificationService.test.ts`:
  - Mock `firebase-admin` with a `messaging().send` jest.fn(); ensure `initFirebase()` doesn't try to load real credentials.
  - Test: `sendDeviceNotification` resolves and returns `{ success: true, messageId }` when `messaging().send` resolves.
  - Test: when `messaging().send` rejects with `code: 'messaging/registration-token-not-registered'`, method returns `{ success: false, error: 'invalid_token', ... }`.

- For `NotificationController.test.ts`:
  - Mock `SensorSettingService.getSettingsByAlat` to return arrays matching conditions.
  - Mock `prisma.sensorSetting.update` to confirm last_notified_at updated.
  - Use `supertest` against `src/app.ts` to call POST `/api/sensor/readings` and assert responses and side-effects.

Commands to run after generation

- `npm run test` (or `npx jest`)

Error handling guidance inside generated tests

- When asserting server unreachable behavior, simulate `axios`/network errors by mocking return values or throwing errors from mocked modules.
- For 401 paths, ensure test clears SecureStore mocks or verifies redirect behavior as needed.

If the workspace contains existing similar tests, extend them rather than duplicating helpers (reuse mock factories placed under `src/__tests__/helpers/`).

Output format

- Create files in `src/__tests__/` with full test implementations.
- Add a short `README.md` note under `src/__tests__/README.md` explaining how mocks are organized and how to run only notification tests (example `npx jest src/__tests__/NotificationService.test.ts -i`).

When invoked with the argument `test`, produce the full test files described above and place them into the repository file system.
